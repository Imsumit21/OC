## Summary

The cohort spine is sound as a volume engine. A run that reads all 109 candidates' notes makes about 165–185 calls. But three things stop it meeting both targets as designed.

1. **The 120-call floor is not guaranteed.** 69 of the 78 non-title Arthur candidates are obviously off-topic by title (icon generator, Plague Race UI, haptics, quests). The 9 hidden members all have gameplay-sounding titles. A title-triage run reads about 55 notes and still gets every member row right, for about 110–125 calls. A run that skips Arthur's tickets lands near 70–90.
2. **The average will probably land at 82–90%, not 62–65%.**
   - Most levers are found by nearly every run: card comment, calendar attendees, knobs-sheet Live tab, notes read in a loop.
   - Three replaced-by cells are stated in the notes outright.
   - Several "traps" fall to a rule the card names itself.
   - Only the Gmail reply (about 65–80% found) and the Confluence comment (about 40–50% found) behave like real levers. The Confluence comment decides one row.
3. **Rule 6 is ambiguous and under-used.** It says "anything Done in Linear that players don't actually have goes back to Todo", but the design writes back only ZOM-303. Eleven Done "Editor only" tickets, and arguably the Done "Replaced" ones, fit the same wording. That is a unique-ground-truth risk. It is also the cheapest honest source of extra calls and per-ticket decisive rows.

Counts: **Blocker 2 · Major 11 · Minor 5**

## Call estimates

Overhead (calls other than `linear_list_comments`) in the Douglas runs was 93–129, of which 14–25 were GitHub review reads. Robert's runs had 100–121. Here the task-specific GitHub load is only about 3–6 calls. Fixed overhead is therefore about 55–75, counting discovery across 9–10 services, 5–8 enumeration pages, `ToolSearch`, the sheet and Drive writes, the Slack reply, the Linear write, and read-backs.

| Run style | Notes read | Total calls | Correct? |
|---|---|---|---|
| Lean and fully correct (all 109 candidates, no re-reads) | 109 | about 165 (150–185) | yes |
| Typical Opus (loop over everything, some re-reads) | 109–130 | 175–210 | yes |
| Title-triage (31 title and amend tickets plus about 25 gameplay-sounding Arthur tickets; skips icons, UI, quests) | about 55 | about 110–125 | mostly yes; ZOM-392 and all 9 members are caught by title |
| Lazy (31 title tickets plus the card comment, no Arthur sweep) | 31 | about 70–95 | misses 9 members and the counts |
| Subagent delegation of the sweep [U] | 109 inside a subagent | top-level count could be about 50–70 | yes |

**Probability that all six runs make ≥ 120 calls: about 35–50%.** Douglas runs ranged 169–246 with 74–146 note reads. Robert run 3 made only 127 and run 1 made 146 with 23–28 reads. Across 12 completed runs, 2 sat within 10 calls of the floor.

**What would push the count up honestly:**
- Make rule 6 explicit for all Done tickets that are not Live (+11 to +16 updates and as many comments).
- Add per-ticket cut-date evidence in GitHub (see finding 12).
- Add a second per-ticket read on about 12 members, such as a revert or reopen comment on a different ticket.
- Add a per-platform check against Android 0.3.133.

## Verdict

- **Not ready for SQL as a 62–65% design.** The volume engine is real, but the 120-call floor depends on Opus not triaging by title, and the average depends on levers that Opus reads almost every time.
- **Before writing SQL**, do four things: resolve the `linear_list_issues` query behaviour [U], decide rule 6, seed non-title members with off-topic titles, and add two or three levers on habits that actually split (Gmail-only-by-raw-event, Confluence comment with two rows, GitHub merge date against the cut).
- **Then project** with `tools/difficulty_stats.py` against the 12 completed baseline runs and report the probability that all gates pass, not just the mean.
