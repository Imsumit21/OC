# 01b Red-team review (reviewer B): rb-winddown-closeout design

Summary. The design is coherent and the truth table is internally consistent (checked: 31 rows sum to 9,651.14; the Keep and Hold rows sum to 1,071.01). It will probably miss both author targets, for two reasons.

1. **Call volume.** The 164-call budget assumes 20 separate Gmail receipt reads. The catalog has `gmail_get_messages_batch(message_ids)`. 13 of the 17 seeded receipts also share the literal string "Visa ending 4417", so one `gmail_search_messages(query=...)` plus one batch read replaces about 20 calls. I estimate a lean correct run at about 135-150 calls and a typical Opus run at 155-185. At least one run of six landing at or below 150 is more likely than not.
2. **Difficulty.** Every hidden source is pre-announced. The Slack ask names the keep list, "the replies under it", Sunset's checklist, SVB's card terms and the conventions doc. The conventions doc then names the ledger, the thread amendments, the bot notice, shared costs-tab lines and the Sunset review call. Sunset's mail names the calendar call and the Confluence page. A "follow every pointer" trait finds all nine levers, so the levers are strongly correlated. The Linear comments also carry many decisive values in plain words: Vercel "bills on the 22nd", Workspace "invoices on the 1st, svb card", Carta "renews jul 14, $2,400", GitHub "kubllc card ... $16/mo", CodeRabbit "2 seats at $24", and the "nothing back yet" status cues. A lean run that never reads Gmail, Calendar, Trello or GitHub still gets roughly 55-65% of cells right.

Predicted per-run score (pass rate on the weighted rubric): mean about 80-85%, SD about 0.06-0.09. Perhaps 20-30% chance the average lands under 75%. Failures cluster in one pattern (precision slips on the 31x6 cells plus Singular/Meta/boundary rows), so the largest failure pattern probably exceeds 50%.
