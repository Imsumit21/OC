Here is the red-team report for the Task-Authoring Harness. The findings are ranked by severity, starting with exploits that allow models to silently break the validity or difficulty of the task while passing all automated gates.

### 1. Ghost Anchors & Unenforced Incorporation (Severity: CRITICAL / Invalid Task)
* **Location:** `Hardness_Manifest_Spec.md` (`ask_fragments.delegated_by_record` / `incorporated_via`) and `01_Scenario_Design.md` S4.
* **The Exploit:** A task requires a deep delegation lattice (Anchors → Hub → Spokes) so requirements are properly incorporated. The authoring model generates valid JSON graph edges in `incorporated_via` and points `delegated_by_record` to a valid injected SQL row ID. However, the injected text for that SQL row contains *no actual delegation language* (e.g., it just says "Here is the list", with no instruction to follow it). The agent has no logical reason to follow the chain, breaking Incorporation (QC rail).
* **Why the current gates miss it:** `hardness_gate.py` only performs a structural graph check (verifying the JSON edges exist, no cycles, and the IDs exist in the SQL). It does not read the natural language inside the SQL row to verify the delegation is explicitly stated.
* **Concrete Mechanical Fix:** Add a `delegation_keywords: []` array property to the `ask_fragments` schema. Require `fact_check.py` to assert that at least one of the exact keyword phrases (e.g., "refer to the hub", "check the ticket") appears in the text of the SQL row specified by `delegated_by_record`.

### 2. Pre-Solving via Bulk Leaks / The "No-Leak" Gap (Severity: HIGH / Easy Task)
* **Location:** `01_Scenario_Design.md` S2 (Shortcut audit), `01_Universe_Injection.md` S4, and `Hardness_Manifest_Spec.md` (`cohort.evidence_surfaces`).
* **The Exploit:** The extreme profile requires ≥ 500 necessary calls, primarily achieved via ≥ 300 per-record calls. The model correctly seeds the deciding facts in a non-bulk surface (e.g., `linear_list_comments`) and documents `why_no_bulk` in the manifest. However, the model *also* accidentally or lazily injects the exact same decisive facts into a bulk-readable surface (like the Linear issue `description` or a single Slack channel topic). An agent can now solve the 300-call task in 1 bulk call.
* **Why the current gates miss it:** `fact_check.py` only verifies that the declared facts *exist* in their designated `must_appear_in` records. It does not verify that the facts *do not exist* in easy-to-reach, bulk-fetchable columns. The shortcut audit is just self-attested text.
* **Concrete Mechanical Fix:** Introduce a `--no-leak` flag to `fact_check.py`. It must extract all values from `facts` mapped to the cohort spine and scan all non-`must_appear_in` seeded text columns (especially ○ carriers and bulk endpoints). If a per-record fact is found outside its designated home, the gate fails.

### 3. Evading the Human-Authorship Boundary via "Constraints" (Severity: HIGH / Spec V2 Violation)
* **Location:** `GEN_EXECUTION.md` §2 (Human-authorship boundary) and `01_Universe_Injection.md` S6 (Constraints for the prompt brief).
* **The Exploit:** Spec V2 strictly prohibits the model from drafting prompt text or suggesting replacement wording. However, S6 explicitly instructs the model to output "Anchors and how they may be named". The model can bypass the boundary by writing: `how they may be named: "Please find the release-readiness control and build the wind-down list."` The human then blindly transcribes this, entirely subverting the prompt-drafting ban.
* **Why the current gates miss it:** The `stage_gate.py boundary` check looks for obvious phrasing like "suggested wording" or "could say". Because the playbook explicitly *asks* for "how they may be named", it creates a semantic blind spot where full imperative sentences are accepted as "constraints".
* **Concrete Mechanical Fix:** Alter S6 in the injection playbook to read: `"Anchors and allowable noun-phrase synonyms only (no verbs, no imperative framing)"`. Update `stage_gate.py boundary` with a regex/NLP check that hard-fails the `04_Prompt_Writing_Brief.md` if the anchor naming constraints contain imperative verbs or phrases longer than 4 words.

### 4. The Coherence-Trap Decoy Contradiction (Severity: HIGH / Invalid Task)
* **Location:** `01_Scenario_Design.md` S3 (Hidden authorities) vs. S8 (Coherence rail) and `01_Universe_Injection.md` S7.4.
* **The Exploit:** S3 mandates placing a decoy authority that "differs on a decisive clause" (e.g., the true authority says "Cut-off is Thursday"; the decoy says "Cut-off is Friday"). S3 also bans "self-advertising cues on decoys or superseded versions" (like "draft"). Because the decoy cannot be explicitly superseded, the task now contains two parallel, identically-scoped records with contradictory rules. This explicitly violates the `1_Prompt_Eval.md` §3.2 Cross-Service Coherence rule (Semantic/Quantitative contradiction).
* **Why the current gates miss it:** `base_check.py` and `sql_lint.py` cannot easily detect logical contradictions in prose. The gate passes it because it has a `decoy_seeded_ids` entry. The Evals, however, will hard-fail the task for lacking Unique Ground Truth.
* **Concrete Mechanical Fix:** Clarify S3 in `01_Scenario_Design.md`: `"Decoys must apply to a demonstrably different scope (e.g., a different game, team, or region) so their differing clause is factually true for that scope but logically inapplicable to the assigned task, preventing QC Coherence failures. Never use identical scopes with contradictory rules unless explicitly temporally ordered."`

### 5. Broken Timestamps in Supersession Traps (Severity: MEDIUM / Invalid Task)
* **Location:** `Hardness_Manifest_Spec.md` (`traps[].version_records`) and `01_Universe_Injection.md` (SQL Validate).
* **The Exploit:** A supersession trap requires multiple versions of a rule/record to exist, with the newest overturning the older ones. The model lists the records in `version_records` (oldest first). However, in the generated SQL, the model injects the "wrong reading" with a timestamp *newer* than the "resolver" record. The agent will read the wrong reading as the newest, making it the ground truth, and the task becomes unsolvable.
* **Why the current gates miss it:** `hardness_gate.py` checks that `version_records` has ≥ 2 elements and that the string IDs exist in the SQL. It does not extract or compare the actual chronological timestamps (`created_at`, `ts`, `date`) of those IDs in the generated SQL.
* **Concrete Mechanical Fix:** Update `hardness_gate.py` (or `base_check.py`) to query the timestamp columns for every ID listed in a trap's `version_records` and mechanically assert they are strictly temporally increasing (oldest to newest).

### 6. Faked "Independent" Chains (Severity: LOW / Shallow Artifact)
* **Location:** `Hardness_Manifest_Spec.md` (`chains`) and `01_Scenario_Design.md` S5.
* **The Exploit:** The extreme profile demands ≥ 3 independent chains with "distinct root causes". An authoring model can simply create 3 identical linear discovery paths for 3 different records (e.g., Slack → Issue → PR) and pass the gate by typing arbitrary distinct strings into the `root_cause` field (`"slack message"`, `"linear comment"`, `"pr review"`). The resulting task is highly repetitive and lacks true mechanical diversity.
* **Why the current gates miss it:** The gate merely evaluates `len(set(root_causes)) >= 3` on arbitrary strings. It does not enforce that the root causes represent actually distinct hardness mechanisms.
* **Concrete Mechanical Fix:** Map `root_cause` in the manifest JSON schema to a strictly validated Enum containing the exact 21 techniques from `Hardness_Mastery.md` (e.g., `A1_stale_summary`, `A12_hidden_authority`, `A14_reply_chain`). Enforce the `len(set()) >= 3` check against this enum.
