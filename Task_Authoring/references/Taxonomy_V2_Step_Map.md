Find and return specific information across connectors, including extracting structured values from documents or records.

**Examples:**

### Screen 12 — Task Complexity Dimensions

*instructions*

# Task Complexity Dimensions 🎚️

Use these three levers to increase the realism and difficulty of your task. They can be combined — a single task can use one, two, or all three.

---

##### 🌫️ 1. Ambiguity

**The prompt under-specifies by design; the agent must resolve the gaps via stakeholders or the universe.**

Instead of spelling out every detail in the prompt, **plant the missing context in the universe** (emails, Slack messages, docs, tickets, calendar events) and keep the prompt deliberately vague. The agent has to discover what it needs by investigating.

**How to do it**

1. Identify the key details the agent needs (dates, names, priorities, constraints).
2. Remove them from the prompt — keep it short and natural.
3. Plant those details across the universe — Slack threads, email chains, doc comments, tickets, spreadsheet notes.
4. Add some noise — related-but-irrelevant info nearby so the agent has to separate signal from noise.

**Example**

- **❌ Over-specified:** *"The Q1 board deck on Drive has a revenue figure that disagrees with the finance sheet in row 47. Fix the deck and email Frederick."*
- **✅ Ambiguous:** *"Frederick mentioned the board deck numbers looked off — can you look into it?"*
- **🔧 Injection:** a Slack message from Frederick — *"one of the charts looked wrong, not sure which"* — with the real discrepancy sitting between the Drive deck and the Sheets data.

---

##### 🔄 2. Dynamic Change

**Superseding information the agent meets in sequence — its picture of the situation changes as it digs.**

Set up the universe so that what the agent learns early gets overturned by what it finds later. This tests whether it detects the change and adjusts, rather than acting on stale assumptions.

**How to do it**

1. Create an initial state the agent discovers first (a meeting on Thursday, a ticket marked "low priority").
2. Plant a contradicting update it reaches later (a newer Slack message moving the meeting, an email escalating the ticket).
3. The agent must reconcile the conflict and act on the most current information.

**Example**

- A Linear ticket says the deploy is Friday.
- A Slack message two hours later: *"customer escalation — we're pushing the deploy to Wednesday, update the checklist."*
- The agent must notice the Slack update supersedes the ticket and act on it.

> 🧭 Discovery order is what makes this land: plant the correction where a plausible investigation path reaches it *second*, after the thing it overturns.

---

##### 🧩 3. Multi-Source

**Information split across 3+ sources with distractors; sources may disagree.**

The agent can't get the full picture from any single system. It must pull from multiple tools, cross-reference, resolve conflicts, and synthesize — while ignoring red herrings.

**How to do it**

1. Spread the required information across at least 3 systems (e.g., Gmail + Sheets + Linear + Slack).
2. Add distractors — similar-looking but irrelevant data (old threads, archived tickets, draft docs).
3. Introduce disagreements — two sources say slightly different things; the agent must determine which is authoritative.

**Example**

- Gmail thread with the licensing partner's terms; Sheets model with projected revenue; Trello card with the integration timeline; a newer Slack message where the partner changed a term.
- **Distractor:** an older Doc with a draft term sheet from a *different* partner that looks similar.

---

> 💡 **Combine them.** The strongest tasks stack levers — e.g., an **ambiguous** prompt requiring **multi-source** investigation where one source carries a **dynamic change**.

---

##### 🔑 The move behind all three: Data seeding

Every lever above works the same way — **you put the complexity in the universe, not in the prompt.** *Data seeding* is how you do that: add or edit universe data (a Slack thread, a ticket, a doc, a conflicting spreadsheet) so the difficulty lives in what the agent has to discover.

A common use is keeping the prompt short and natural:

- ❌ **Don't** cram it into the prompt: *"Hi, can you help me do… \[long, detailed instructions\]"*
- ✅ **Do** seed it: put the instructions in a Slack channel, then prompt: *"Can you check #channel-name and follow the instructions there?"*

> ⚠️ Call this **data seeding / injection** — not "SQL injection," which means a security vulnerability.
>
> 🌍 *How* to actually add and edit universe data (chatbot vs. SQL) is covered on the **HarmonyGames Universe** section.

### Screen 15 — Error Injection & Async Wait

*instructions*

## ⚡ Error Injection & Async Wait — Optional Step

The next step lets you **optionally** configure two server-side behaviour modifications. **You can skip this step entirely** — leave both tool pickers empty and click **Next**. Nothing is applied and the run behaves exactly as it does today.

Both settings are applied to **all runs**: the baseline agent run and the rubric verifier. They are **not** applied to the Universe Explorer, so you cannot preview them there.

---

##### 🔴 Inject Forced Errors

Select function(s) that will return an error when called during agent or verifier runs. This simulates a service being down, broken, or unreachable.

###### Error rate — read this carefully

| Rate | Behaviour | Marked transient? |
| --- | --- | --- |
| **1.0** (default) | The tool fails on **every** call. A retry will **never** succeed. This is a permanent outage. | No |
| **&lt; 1.0** | The tool fails on that proportion of calls. A retry **can** succeed. | Yes |

Choose deliberately:

- Want to test whether the agent **retries** a flaky call? Use a rate **below 1.0** (0.5 is a reasonable starting point).
- Want to test whether the agent finds a **workaround** or **escalates**? Use **1.0**.

Do not set 1.0 and then write a rubric that expects a successful retry — that is unpassable.

> ⚠️ **Only 1.0 / 30 / 35 have been exercised so far.** The Obi taxonomy hardcoded those three values, so no task on record has run with a partial error rate or a non-default wait. If you change any of them, treat your first baseline run as a test of the setting itself: open the trajectory and confirm the tool failed at roughly the rate you asked for, and that the delay matches what you set. If it doesn't, report it via the issue form rather than building the task on top of it.

> 🚫 **HARD RULE: YOUR PROMPT MUST STILL BE SOLVABLE WITHOUT THE ERRORED FUNCTION.**
>
> If the only route to the answer runs through a tool you have killed, the task is broken, not difficult. Before you select anything here, name the alternative path out loud and confirm it exists in the universe. Your Oracle Events must show that path.

---

##### ⏳ Make Functions Async (Waiting)

Select function(s) to switch into async mode. The instant version of the tool is **disabled automatically** — you do not need to do anything else — and the agent must instead use the submit-and-wait sequence (submit job → check status → get results), which adds a delay before results come back.

Default delay is **30–35 seconds** per call. You can change it below.

###### ⚠️ Two things that will silently defeat this

**1. Async only affects *search***, **never *fetch***. Every selectable async tool disables a discovery tool, not a retrieval tool. For example, switching Gmail search to async leaves `gmail_get_message` fully instant; switching Linear list-issues to async leaves individual issue reads instant.

> **Consequence:** if your prompt names the exact document, channel, ticket, or file, the agent will fetch it directly and never pay the delay. The wait only bites when the agent genuinely has to **search** to find the thing. Write the prompt so discovery is required.

**2. The agent may bypass MCP entirely.** Agents have been observed skipping the submit-and-wait path by reading the underlying data directly rather than going through the MCP tool. If your task depends on the wait actually happening, check the baseline trajectory and confirm the async calls fired. If they didn't, the wait contributed nothing.

---

##### 🧾 How This Affects Your Oracle Events and Rubrics

If you inject an error or an async wait, the recovery behaviour becomes part of the solution path — which means it has to appear in your OEs and rubrics, **and both have framing rules that error-recovery content tends to violate.**

###### Oracle Events — no non-actions

OEs must describe an observable action or discovery. "The agent does not give up" is not an event.

- ❌ **OE 5:** The Agent does not stall when the search fails.
- ✅ **OE 5:** Establish that the primary lookup is unavailable and recover. `gmail_search_messages` (query: "Season Pass rollback") → returns a server error on every attempt; Agent then reads the same thread from the shared drive copy. **Expected:** the rollback decision and its date are recovered from the drive document, not from mail search.

###### Rubrics — affirmative framing only

Criteria Framing is its own SLA dimension. A single negatively-framed criterion that does not correspond to an explicit prohibition in the prompt **fails**. Error-recovery rubrics are the most common place authors slip.

- ❌ The Agent does not report the data as unavailable.
- ❌ The Agent never abandons the task after the failure.
- ✅ The Agent obtains the rollback date from the shared drive copy after the mail search fails.
- ✅ The Agent states in its final response that mail search was unavailable and names the source it used instead.

The second pair works because the affirmative verb ("obtains", "states") carries the criterion, and the failure is described as content rather than as a prohibition.

---

> 💡 **Tip:** Both pickers are completely optional. If your scenario doesn't need failure or latency, leave them empty and click **Next**. A well-built universe with no injected friction is far better than a broken task with a killed tool.

##### Rules for valid, consistent injection 🔴

Injected data has to hold up under investigation. Before you rely on anything you add, make sure it's:

1. **On the clock.** No date/time is ever after the frozen "now" — **February 14, 2026, 12:00 AM**. No future events written as already done; business messages on weekdays at plausible hours; a record's created time is never after its updated time.
2. **Consistent across services.** If you add a Slack thread about a pull request, that PR must actually exist in GitHub. Names, IDs, dates, and facts must line up everywhere they appear — edit one side, fix the other.
3. **Coherent with the universe.** New data fits HarmonyGames' existing storylines, people, games, and relationships, and doesn't contradict what's already there (e.g., don't set a doc to $65 while a linked sheet still says $35).
4. **Structurally valid.** Records fit the real table schema ([click here](https://static.remotasks.com/uploads/6a5595596cf3031de47f0ea2/7_Universe_Schema.json)) and follow the universe's existing ID formats (e.g., `ENG-####`, `ZOM-###`). No invented fields or malformed IDs.
5. **Reachable & findable.** Evidence the agent needs is readable by your assigned persona (mind the scoped services) and discoverable by a realistic search — no references pointing to records that don't exist, and nothing buried where search can't reach it.
6. **Natural.** Match each service's real voice, length, and formatting. Avoid AI-tells — generic phrasing, repeated boilerplate, implausibly tidy or complete text.
7. **Not pre-solving.** Seed the *situation* and the *evidence*, not the conclusion. The agent should still have to connect the dots.
8. **State matches activity.** A record's status must agree with what happened to it: no ticket marked Closed whose PR never merged, no task Done with an open blocker, no invoice Paid with no payment. A single cosmetic mismatch that doesn't affect solvability is a minor issue, but still fix it.

### Screen 23 — ⚠️ Before You Write: Sound Human, Not LLM

*instructions*

# 🚨 Do NOT Use LLM / AI to Write Your Prompt

**This is the #1 reason prompts get flagged and rejected.** If your prompt reads like it was written or polished by ChatGPT, Claude, or any other AI, it will fail review. Write it yourself, from scratch, in your own voice.

---

##### Write Like a Real Person Types

Think about how you actually type when you're messaging Claude or ChatGPT in your day-to-day life. You don't capitalize every sentence perfectly. You don't proofread. You just type what you need and hit enter. **That's what your prompt should feel like.**

- **Don't capitalize every sentence start.** Real people typing fast don't bother. Mix it up — some caps, some not.
- **Leave in small typos.** A misspelling here and there, a missing word, an autocorrect that didn't quite land — that's how real typing looks. Don't polish it to perfection.
- **Be vague where a real person would be.** Don't spell out every detail. Say "the numbers look off" instead of naming exactly which metric in which spreadsheet. Being vague about *where* things are is good; being vague about *what you want* is not.
- **Be imprecise and casual.** "can you check on the launch stuff" — not "Please investigate the Q1 product launch status across all relevant project management and communication channels."
- **Skip obvious steps.** A real person doesn't say "First look up X, then cross-reference Y, then compose Z." They just say what they need and trust their assistant to figure out how.
- **Use sloppy, natural references.** "whatever julia was talking about," "that revenue thing," "the bug people keep complaining about" — not internal IDs a person would never type. Human-readable titles are fine ("the GEOGAMES spec doc"); opaque ones aren't ("geogames_spec_23mf2ldf02.docx", ENG-2847, an agent_id).
- **Let your sentences run on or pile up.** Real messages aren't perfectly structured paragraphs. They're messy, they double back, they add afterthoughts with "oh and also" or "actually wait".
- **Add realistic ambiguity.** Don't make it 100% clear what "the issue" is or where to find the answer. A good task makes the agent do some detective work.

---

##### Red Flags That Get Prompts Rejected 🚩

- Perfectly capitalized and punctuated throughout — no human types like that in a chat
- Perfectly parallel structure or neatly enumerated steps 1, 2, 3
- Unnaturally complete — nothing left unsaid, every requirement spelled out
- Formal or corporate phrasing ("Please ensure," "It is imperative that," "Kindly proceed to")
- Markdown formatting — headers, bold, bullet points, horizontal rules
- Zero typos, zero messiness — too clean to be real

---

##### The Bottom Line

**Don't use AI to write it. Don't use AI to polish it. Don't over-specify. Be vague, be messy, be human.** Type it the way you'd actually type a message to Claude or ChatGPT when you need something done — casual, imperfect, and straight to the point.

### Screen 24 — Write the Prompt

*goal*

Write the prompt as a **real message from your persona to their AI assistant** — first person, informal, with the messy context a real person would actually include. Don't write a spec sheet; write the way someone talks to their assistant.

The strongest tasks have **two phases**: the agent first has to *figure out what's happening*, then *do something about it*.

> **Example:** "Our Day-7 retention on the latest build dropped off a cliff — check the dashboards to see if something changed after the last update. If it's the new tutorial flow, pull the Linear ticket and flag it to Julia. Also ping the team in Slack."

##### What makes a task strong 💪:

- 🔍 **Investigation + action** — it requires both discovery *and* a follow-up action, not just a lookup.
- 🧩 **Information friction** — the answer isn't in one place; the agent must piece it together across multiple services.
- 🧠 **Implicit requirements** — things a competent assistant would obviously *infer* even if you didn't say them (e.g., check the actual data before filing a bug; don't message investors before internal review). Keep these genuinely inferable, not hidden gotchas — every rubric must still trace back to the prompt.
- 🚧 **Constraints** — budget limits, policy requirements, or approvals the agent must navigate.
- 🎚️ **Task complexity** — revisit the **Task Complexity Dimensions** from earlier and build the strongest ones into your prompt to push difficulty.
- 🔑 **Data seeding** — lean on the data you seeded into the universe; write the prompt so the agent has to dig the answer out of it rather than getting it handed over.

*writingGuideline*

Every prompt must satisfy all of these.

##### Always ✅

**1. Be tool-dependent.** The task must require MCP tools. If it can be answered from general knowledge alone, it isn't a valid task.
- ❌ "What's the best way to improve Day-1 retention?"
- ✅ "Our Day-1 retention tanked after 2.4.1 shipped. Check the dashboards, see what changed, and figure out if it's the new onboarding flow or something else."

**2. Span multiple services.** Pull data from or act across at least 2–3 services. Single-service tasks are too simple.
- ❌ "How many unread emails do I have?"
- ✅ "The publisher flagged a revenue discrepancy. Cross-check the numbers against the finance sheet and the email thread — then brief the team."

**3. Sound natural.** First person, informal, real messy context — like talking to your assistant, not writing a requirements doc.
- ❌ "Query the email service for messages from the publisher. Then query the analytics dashboard. Compose a response email."
- ✅ "The publisher just emailed about our numbers being off — that's never good. Can you dig into what they're seeing and handle the response?"

**4. Be feasible.** Every request must be possible with your persona's tools and read access, and no two instructions can contradict each other. Nothing later in the flow rescues an impossible prompt, so fix it before the baseline.

--- 

##### Never 🚫 

**1. Name tools or parameters.** Let the agent work out *how*.
- ❌ "Use search_emails to find emails from the publisher"
- ✅ "Check what the publisher sent us about the licensing deal"

**2. Pre-solve the problem.** Don't hand over the answer; make the agent investigate and discover it.
- ❌ "The IAP conversion bug is in the checkout flow's price_display function. Fix the Linear ticket."
- ✅ "Players are reporting they see wrong prices in the store. Something's off — figure out what's going on."

**3. Include internal IDs.** No database, persona, or ticket IDs unless a real person would actually know them.
- ❌ "Check Linear issue ENG-2847"
- ✅ "Check what's happening with the matchmaking lag issue"

**4. Announce an injected failure or wait.** If you forced a tool to fail or go async, don't mention it — discovering it is part of the task. Don't name the exact document, channel, or ticket the async search must find (or the agent fetches it directly and the wait never fires), and make sure the answer is still reachable without any tool you killed.
- ❌ "Mail search is down right now, work around it."
- ✅ "Pull the rollback decision and its date." *(let the agent hit the outage and recover on its own)*

**5. Format it like a document.** Write plain, natural prose in full sentences. **Do not use any markdown structure** — no headings (`#`, `##`), no horizontal rules (`---`), no bullet points or numbered lists, no "Requirements/Constraints" sections, and no bold-everything. A real person types a message, not a formatted spec sheet.

❌ **Don't write the prompt like this:**
```
#### Revenue Reconciliation
##### Task
Reconcile the revenue numbers.
##### Requirements
- Pull the finance sheet
- Cross-check the email thread
- Post an update to Slack
---
**Note:** keep the existing column order.
```
✅ "The publisher's revenue numbers look off — can you cross-check against our finance sheet and the email thread, then let the team know what you find?"

**6. Bolt on an unrelated request.** If you can delete a sentence without changing anything else in the prompt, it shouldn't be there. It adds a second task, not depth.
- ❌ "...then raise the tickets. Also can you book a meeting with Julia next week about Q2?"

--- 

##### 📅 Dates

The task's current date is **February 14, 2026, 00:00 UTC** ⚠️. Write any date as an **absolute** value anchored to it (e.g., "February 13, 2026") rather than a relative reference like "yesterday" or "last week." Relative phrasing is fragile in a replayed task and will be flagged.

--- 

##### 🎯 One right end state

Vague about where the answer lives is good. Vague about what you're asking is not.
- ✅ **Discovery ambiguity:** the agent doesn't know where the answer is or which source to trust, but every careful run ends in the same final state.
- ❌ **Decision ambiguity:** two readings lead to two different actions (act now or wait, tell A or B, file in X or Y, "write a doc or just tell me"). This fails.
- If only the wording or channel changes (email vs Slack DM to the same person), that's minor, not a fail.

--- 

##### ✅ Check every fact

Verify every name, date and figure in your prompt against the Universe Explorer, not memory. There are three Marcuses (Marcus Bennett, Marcus Lee, marcus@harmonygames.co), and ENG-#### and ZOM-### are different ticket series. One major factual error fails; two minor ones fail; one minor one is a non-fail.

### Screen 44 — Write Oracle Events First ✍️

*instructions*

# Write Oracle Events First ✍️

While your baseline runs, write the Oracle Events (OEs): the steps a correct agent has to take to solve your task, from the first thing it has to find to the last thing it has to write.

Write them as plain text, not structured JSON. They prove the task is solvable and make writing rubrics much easier afterward.

For each step, cover:

- **Action** — what needs to happen
- **Information** — what has to be found first
- **Tool / Service** — where the data actually lives
- **Parameters** — names, filters, date ranges, values
- **Expected Data** — what the step should return or produce, with the real values

Format each one like this. Plain sentences are fine; no function names or raw IDs needed:

```
OE <n>  <What the step is for, and where to look> (<parameters>)
        Expected: <the actual values it returns or produces, and any trap>
```

**Rules:**
- Cover the full path, including every write the prompt asks for (docs, tickets, messages).
- Don't describe what the final response should say. That's the rubric's job.
- No non-actions ("the agent does not give up", "doesn't stop at the first message"). Say what reading to the end actually finds.
- No redundant or unnecessary events.
- Every Expected line must match the universe exactly. Check the dates, counts and totals.

---

##### Oracle Events serve two purposes:

1. **Prove solvability** — demonstrate that the task can be solved and that you understand the correct solution path
2. **Drive rubric writing** — OEs identify which actions exist, and the three-condition test decides which process rubrics to write

---

##### How OEs connect to rubrics:

**Step 1:** Write all **Outcome rubrics** first. For every action in your OEs, write an Outcome rubric verifying the action result, plus a content rubric if specific requirements exist. For every key fact the user asked to be told directly, write an Outcome rubric for the final response.

**Step 2:** Review the full rubric set for gaps no Outcome can cover. After writing all Outcomes, ask: *is there any requirement — explicit or implicit — that none of my Outcome rubrics can verify?* The primary case is **ordering between actions** (A must happen before B, but both Outcome rubrics pass regardless of sequence). In rare cases, **source verification** may also qualify — where the correct answer is available in a shallow source and the Outcome genuinely cannot be made specific enough to prove the agent checked the authoritative source. These are your candidates for Process rubrics.

**Step 3:** Apply the **three-condition test** to each candidate:
1. Required by every valid solution path (or phrased broadly enough to allow alternatives).
2. A stricter Outcome rubric cannot capture the same requirement.
3. The rubric describes a behavioral property, not an execution trace.

If any condition fails, tighten the Outcome instead. If all three hold, write a Process rubric. When in doubt, default to Outcome.

---

##### Example 🧾

If the prompt is: *"Send an email to Chloe from Fatimah about a relocation proposal"*

Your Oracle Events might look like:

```
OE 1  Look up Fatimah's and Chloe's email addresses in Contacts.
      Expected: fatimah.al-rashidi@moveops.com and chloe.vance@moveops.com.
```
→ Read/lookup action. The Outcome rubrics for the email already prove this happened — no Process rubric needed.

```
OE 2  Send an email from Fatimah to Chloe about the relocation proposal (Gmail).
      Expected: one sent email from fatimah.al-rashidi@moveops.com to chloe.vance@moveops.com with a subject and body about the relocation proposal.
```
→ Action → goes into Outcome rubrics.
→ Outcome (action result): "The Agent sends an email from fatimah.al-rashidi@moveops.com to chloe.vance@moveops.com."
→ Outcome (content): "The Agent uses a subject line related to a relocation proposal (e.g., 'Relocation Proposal for GreenStack' or similar)."

**Process rubrics:** None. The prompt's deliverable is the email. The Outcome rubric already verifies it was sent — no ordering constraint exists, and no stricter Outcome is needed.

---

> **Note:** A single action in your OEs can generate both an Outcome rubric and a Process rubric. For example, if the prompt requires the agent to notify legal *before* scheduling a contract signing meeting, the scheduling itself gets an Outcome rubric in Step 1, and the ordering requirement gets a Process rubric in Step 2 — because the scheduling Outcome alone cannot prove the notification came first.

> The rule is not "write actions → Outcome, reads → Process." It is **"Outcome first, Process only when no Outcome can verify the requirement"** — and that requirement can attach to any action in your OEs, regardless of whether it's a write or a read.

### Screen 59 — Difficulty & Failure-Pattern Check

*instructions*

## Difficulty & Failure-Pattern Check

Before continuing, confirm the baseline meets all rules below. The next step computes all metrics automatically — if any check fails, revise the prompt or universe first.

---

###### Key terms

- **Weighted rubric pass rate** — for a single rollout: the sum of weights of rubrics it passed divided by the sum of all rubric weights. Rubrics with higher weights (1–5) contribute more to the score. The *average* weighted pass rate is the mean of this across all completed baseline rollouts.
- **Pass@1 rate** — the fraction of completed baseline rollouts where **every rubric passes** (i.e. 100% weighted pass rate). This is different from the average weighted pass rate. A pass@1 of 20% on 6 rollouts means at most 1 rollout passed all rubrics.
- **Distinct failure pattern** — two failing rollouts count as **different patterns** if they differ in **at least 2 rubric results** (i.e., at least 2 rubrics have different pass/fail outcomes between the two runs). If they differ on only 0 or 1 rubrics, they're considered the **same pattern**.
- **Failing rollout** — any completed baseline rollout that failed at least one rubric.

---

###### Rule 0 — Completed rollouts

- All **6 rollouts** must be completed before proceeding.

###### Rule 1 — Pass@1 rate

- Pass@1 rate must be **≤ 50%** (at most 3 out of 6 rollouts may fully pass — 4 or more passing means the task is too easy)

###### Rule 2 — Failure concentration

- At least **2 distinct failure patterns** across failing rollouts
- No single pattern accounts for **more than 50%** of failing rollouts (exactly 50% is OK)

**Why this exists:** If every failing rollout fails in the exact same way (same rubrics fail every time), the task has a single bottleneck rather than genuine multi-dimensional difficulty. We want the agent to struggle in **different ways** across runs — that means the task tests multiple capabilities, not just one.

**How pattern grouping works:**

Two failing rollouts are grouped into the **same pattern** if their rubric results differ on **fewer than 2 rubrics**. This means:

- Rollout A fails rubrics {X, Y, Z} and Rollout B fails rubrics {X, Y} → they differ on only 1 rubric (Z), so they're the **same pattern**
- Rollout A fails rubrics {X, Y, Z} and Rollout C fails rubrics {W, V} → they differ on 5 rubrics, so they're **different patterns**

The 50% rule then checks: take the largest group of rollouts that share a pattern — if that group is more than half of all failing rollouts, the failures are too concentrated.

**Example:**

| Rollouts | Failed rubrics | Pattern |
| --- | --- | --- |
| 2 rollouts | A, B, C | Pattern 1 |
| 2 rollouts | A, B | Pattern 1 (only 1 rubric different from A,B,C) |
| 2 rollouts | D, E | Pattern 2 (≥ 2 rubrics different) |

Pattern 1 has 4 of 6 failing rollouts = 67% → **FAIL** (exceeds 50%). The failures are too concentrated in one pattern — revise the task to create more diverse failure modes.

###### Rule 3 — Average weighted rubric pass rate

- The average weighted pass rate across the 6 completed rollouts must be **under 90%**.

**Why this exists:** pass@1 only counts runs that got everything right. A task can have 0% pass@1 while every run scores 85% — the agent nearly solves it every time. This rule catches that.
